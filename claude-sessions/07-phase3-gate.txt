  Where I agree, and where I'd change your position

  1. Emergency: agree, with three additions.
  - It runs in handle() before the router and before the pending-yes check. It
    clears pending.
  - Normalise first: NFKC, lowercase, strip punctuation, collapse repeated
    letters. Match phrases in Latin and Devanagari: seene mein dard, saans nahi 
    aa rahi, behosh, khoon bah raha, zeher, suicide, and so on.
  - Bias to false positives. A false alarm costs one 108 message. A miss costs a
    patient. So there is no negation handling ("I had chest pain last year"
    also fires).
  - Add one cheap second layer in place of a model layer. The router's schema
    gets a boolean emergency_suspected. The router already runs on every
    message, so this costs no extra call. If it is true, we take the same
    emergency path. That is about 5 lines.
  - The reply is a fixed text in three languages (108, the 24-hour ER at the
    main entrance, no advice). The flags are emergency=true, handoff=true, plus
    a staff-queue record.

  2. Confirmation: agree, and here is how it fits our runtime.
  - The write tool is the only thing the model calls. The before_tool hook
    decides what happens:
    - No pending action, or the params differ from the stored ones: Pause. Code
      builds the pending action {tool, params, display, key=uuid4, agent}. The
      read-back text is built from hospital data fetched in that turn, never
      from model text.
    - A pending action marked confirmed, with the same params: Allow.
  - The write tool ignores the model's params and runs the stored ones with the
    stored key. A different model call after the yes can't change what runs.
  - The reply on a pause is the code's read-back. The model's post-pause text is
    thrown away. A history transform replaces the last assistant message with
    the read-back, so it is stored together with pending. We already have the
    history_transform hook for this.
  - A pending action lives for exactly one turn. The next message either is a
    strict yes or clears it ("wait, make it 6pm" clears it, and the agent
    re-proposes). This needs no timers, and an old pending action can never be
    confirmed by a stray "ok" two hours later. The cost is a little friction.

  3. Strict yes: agree.
  - A message is a yes only if its whole normalised text is in a set. Examples:
    yes, yes please, ok, okay, confirm, go ahead, haan, haan ji, theek hai, kar 
    do, haan kar do, हाँ, ठीक है, कर दो.
  - "yes but make it 6" is not a yes. A message with a ? is not a yes.
  - A yes skips the router and goes straight to pending["agent"]. That saves a
    call and removes the router as a way to misroute a confirmation.
  - The owning agent gets a system note ("the patient confirmed, call the
    tool"), and the hook then allows the call.

  4. Ownership: agree, and the same fetch does three jobs.
  - For reschedule, cancel and payment link, the hook fetches
    /appointments?phone= or /bills?phone= itself, in that turn. It requires the
    id to be in the result, the appointment to be booked, or the bill to be
    unpaid.
  - The fetched record is also the source for the read-back and for the 4-hour
    check. The model and the facts note are never the source.
  - The hook runs again on the confirmed call, so the checks are fresh at
    execution time.
  - A failed fetch means Block. It fails closed.
  - Booking has no id. Its ownership is the injected phone.

  5. 4-hour rule: agree, with the handoff set in code.
  - A Block alone isn't enough, because the model might not call a staff tool
    afterwards. The hook itself writes data["handoff"] = reason, plus a
    staff-queue record, then blocks.
  - When code set the handoff, the service replies with a fixed three-language
    template for that reason. It does not use the model's text.
  - Condition: start - now < 4h goes to staff, and that includes a start that
    has already passed. A start of exactly 4h is allowed. Assignment.md says
    "less than 4 hours", so this matches.
  - /now unreachable, or an unparseable start: no change and a handoff.

  6. Staff tool and two strikes: agree, with these details.
  - The mock has no staff endpoint. So contact_staff(reason) writes to a
    service-side queue (an in-memory list mirrored to traces/handoffs.jsonl) and
    sets handoff. The agents are only allowed to say "staff has been told"
    after it returned Done. That fixes finding 1 from the calm run.
  - It is on all three specialists. The prompts change from "offer staff" to
    "call contact_staff when the patient asks for a person or you can't help".
  - Watch scenario 09. Insurance is not in the docs. If info calls contact_staff
    unprompted, handoff goes true. That check allows it, but unseen scenarios
    may not. I'd say: info answers "I don't know" and offers staff, and only
    calls the tool when the patient asks.
  - A strike is a turn that ends in a failure template. That means a failed loop
    or an Unknown write outcome. The counter lives in state. It resets on any
    done or paused turn. At 2 the patient gets the handoff template and
    handoff=true.
  - I'd drop "same request" and count consecutive failed turns. It is simpler
    and errs towards a person.
  - This deviates from 2.3, which says a router fallback is a strike. A router
    fallback where the specialist then answers is not a failed turn, so it won't
    count.

  What each write does

  Tool: book_appointment
  Hook checks: phone is injected; read-back from /doctors
  Executor: key from pending, atomic, retry on 503 only
  Verify after 503/timeout: list_appointments has a booked one at that doctor
    and start
  ────────────────────────────────────────
  Tool: reschedule
  Hook checks: ownership, booked, 4h
  Executor: atomic, no key, not retried
  Verify after 503/timeout: the appointment's start equals the new start
  ────────────────────────────────────────
  Tool: cancel
  Hook checks: ownership, booked, 4h
  Executor: same
  Verify after 503/timeout: the status is cancelled
