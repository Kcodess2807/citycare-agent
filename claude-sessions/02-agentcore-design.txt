  1. Tool registry

  - A Tool holds a name, a description, a pydantic input model, an async
    run(input, ctx), a timeout_s, and max_retries with a retry_on set.
  - It also has an idempotent: bool flag. That flag is the only thing the
    runtime knows about retries. The runtime knows nothing about bills or
    appointments.
  - The JSON schema sent to the model comes from model_json_schema().
  - If the model's arguments fail pydantic validation, the registry returns a
    tool_result with is_error: true and the validation message. The model sees
    it and can fix the call.
  - An unknown tool name gets the same treatment, with the list of valid names
    in the error.
  - If a tool raises, the error is also sent back to the model as an error
    result and written to the trace. It never crashes the turn.
  - agentcore never imports hospital code. The hospital tools live in
    agent_service/ and register themselves.

  2. Agent loop

  It is our own loop on AsyncAnthropic.messages.create, with the SDK's
  max_retries=0 so we control every retry.

  Per-turn limits:

  ┌──────────────┬───────────────────┬──────────────────────────────────────┐
  │    Limit     │       Value       │                Reason                │
  ├──────────────┼───────────────────┼──────────────────────────────────────┤
  │              │ 8 model calls per │ A booking needs roughly 3-5 calls. A │
  │ Step limit   │  agent per turn   │  cap of 8 stops loops without        │
  │              │                   │ hurting real flows                   │
  ├──────────────┼───────────────────┼──────────────────────────────────────┤
  │ Per-turn     │                   │ The runner waits 180s. Each call     │
  │ wall budget  │ 45s               │ gets min(own_timeout,                │
  │              │                   │ remaining_budget)                    │
  ├──────────────┼───────────────────┼──────────────────────────────────────┤
  │ Identical    │ the 3rd repeat    │ Catches a model stuck repeating      │
  │ tool call    │ with the same     │ itself                               │
  │              │ args is blocked   │                                      │
  └──────────────┴───────────────────┴──────────────────────────────────────┘

  Model calls:
  - Timeout is 30s. Haiku usually returns in a few seconds and Sonnet with
    thinking in 10-20s.
  - We retry on 429, 5xx, 529, connection errors and timeouts: 2 retries, so 3
    attempts.
  - Backoff is min(8s, 1s * 2^n) with full jitter, and we honour retry-after
    when present.
  - We never retry 400, 401 or 403.
  - max_tokens is 256 for the router and 1024 for specialists. WhatsApp replies
    are short.

  Stop reasons, each handled explicitly:
  - end_turn: return the text.
  - tool_use: run the tools, append the results, loop.
  - max_tokens with text: return the text and flag it in the trace. max_tokens
    while building a tool call: treat as a failed step, because a truncated call
    must never run.
  - refusal: return a safe fixed message, set handoff, and log it.
  - pause_turn: continue the loop.
  - Context overflow or any unknown reason: fail closed with a handoff.
  - Anything the loop can't finish (step limit, budget, repeated failures)
    returns a LoopResult(status="failed", reason=...). It never raises to the
    caller, so /chat always has something honest to say.

  Tools in one step run concurrently with asyncio.gather. Writes are not run
  concurrently with other writes.

  3. Hooks

  Four points: before_model, after_model, before_tool, after_tool. Each hook
  returns one of three results:
  - Allow
  - Block(reason): for a tool call, the reason goes back to the model as an
    error tool_result. For a model call, the turn ends with that reason.
  - Pause(prompt): the turn ends, the prompt goes to the patient, and the
    pending state stays in the session. The patient's next message resumes it.

  Hooks run in registration order and the first non-Allow result wins. A hook
  that crashes counts as Block (fail closed). The runtime only provides the
  mechanism. The actual rules (ownership, confirmation, 4-hour rule, emergency)
  are hospital logic, so they live in agent_service/ in Phase 3.

  4. Trace

  - It is a list of events per session, stored in the session store. GET 
    /trace/{session_id} returns it.
  - Event types are model_call, tool_call, hook_decision and stop.
  - Every event has a monotonic timestamp, duration in ms, inputs and outputs
    (truncated to about 2 KB each), and attempt number.
  - Model events also carry input, output, cache-read and cache-write tokens,
    and cost in USD from a price table in the code. Prices will be checked
    against the docs, not taken from memory.
  - Every event carries the trace_id that /chat returns, and each turn gets its
    own id.
  - The trace never holds the API key, because the key is never in anything we
    log.

  5. Session store

  - It is a small async Protocol: get(session_id), save(session) and
    delete(session_id). An in-memory dict implements it. Redis can replace it
    without changing callers.
  - A session holds messages, state: dict (pending action, payment-link cache,
    failure counters), trace, and last_active.
  - Each session has an asyncio.Lock, so two messages on the same session run
    one after the other. Different sessions run in parallel.
  - Idle sessions expire after 30 minutes.
  - History is capped at 40 messages. The cutoff never splits a tool_use from
    its tool_result, because the API rejects that.
  - Cache breakpoints go on the system prompt and the tool list, since they
    never change between turns.

  6. Hospital client

  This is not agentcore, but it sits next to the tool registry:
  - httpx.AsyncClient with a 6s timeout. That is above the mock's 2.0s maximum
    latency, and still short enough to fit 3 attempts in the budget.
  - Reads and payment_link retry 503 up to 2 times, with backoff of 0.5s then
    1s, plus jitter.
  - book retries only with the stored idempotency key. reschedule and cancel are
    never retried blind. After a 503 or timeout on them we read the real state,
    as decided in 0.5.

  Rough worst case for one booking turn

  About 4 model calls at 3-6s each and 4 hospital calls at about 1.2s each is
  roughly 20s. One retry of each adds about 8s. That fits in 45s with some room.
  We will measure this against chaos before trusting it.

  Where I'd like your call

  1. Step limit of 8 and budget of 45s. Are you OK with these as starting
     values?
  2. Pause semantics. Should confirmation pauses end the turn (my
     recommendation), or should the loop wait for the next message inside the
     same call? Ending the turn is simpler and lets the store carry the state.
  3. Refusal and context overflow. Handoff is my pick for both. Do you agree?

● I've updated docs/design-log.md with a new "Phase 1: agentcore design" section
  (1.1 to 1.9). No code yet. Answers by your numbering:

  1. Sync fake, async loop. The loop is async only. I won't edit the provided
     tests/fake_claude.py. A small test-side AsyncFake wraps it and exposes an
     async create. Backoff sleeps are injectable so retry tests don't wait.
  2. Partial text. You're right, my earlier design broke that rule. On
     max_tokens the response is discarded and never put in history or shown. The
     step is retried once with double max_tokens (cap 8192), and if it
     truncates again the turn fails to a handoff. A cut-off tool_use is
     discarded the same way.
  3. Thinking vs max_tokens. I checked the docs.
     - Thinking tokens count inside max_tokens and are billed as output, so 1024
       was too low. The caps are now router 1024 and specialists 4096.
     - Sonnet 5.5 rejects thinking: disabled with a 400. Haiku 5.5 allows it at
       high effort or below.
     - Prompt text like "think less" is documented as unreliable, so effort is
       the lever. It is fixed per agent, because changing it invalidates the
       cache.
     - We don't send thinking or temperature. Router effort is low. Specialists
       start at low and go up only if measurement shows a quality gap.
     - One risk I haven't verified: trimming history may break the
       thinking-block check. I'll test it with one real call early in Phase 1.
  4. Latency. The two numbers were unmeasured guesses: 10-20s assumed Sonnet
     with thinking, 3-6s assumed none. Everything is now in a config object.
     Provisional values are model timeout 60s, turn budget 90s and hospital
     timeout 6s, with step limit and retries as before. A tools/measure.py will
     run about 5 conversations against the mock with chaos on, per candidate
     model and effort. It reports p50/p95 per model call, tool call and turn,
     plus cost, which I estimate at under $0.30. Timeouts then become about 2-3x
     the measured p95.
  5. Pause/resume.
     - A blocked write still gets a tool_result, and other calls in that step
       get "skipped". The model then writes the read-back in the patient's
       language.
     - The pending action sits in session.state: params, read-back facts, key,
       status and expiry.
     - Every tool_use always gets a result, and history is committed atomically
       at the end of the turn, with a pairing check before commit and rollback
       on failure.
     - On "yes", code runs the stored action through the same registry, hooks
       and trace, not the model. How code recognises the yes is still the Phase
       3 decision.
  6. Writes are never cut off. The budget is checked only before starting
     something. A write tool is one unit (write, then verify on 503 or timeout)
     that runs shielded from cancellation. A write starts only if the remaining
     budget covers its ceiling of about 30s. Otherwise nothing is changed and
     the patient is handed off.
  7. Retries in one place. The hospital client is dumb: 6s timeout, typed
     errors, no retries. One with_retries helper in agentcore serves model calls
     and tools, and each tool declares its own policy. reschedule and cancel
     get 0 retries and verify instead.
  8. Write detection and sequencing. A tool declares kind: read|write. The
     runtime uses it for three things:
     - writes are shielded from cancellation;
     - there is no retry unless the tool is idempotent;
     - at most one write per turn.

     Tools run sequentially. Parallel reads would save about 1.2s each under
     chaos, which isn't worth the complexity yet.
  9. Traces. TraceStore is separate from SessionStore, so traces outlive the
     30-minute session expiry. It is an in-memory LRU of 1000 sessions plus a
     gitignored JSONL file under traces/. The JSONL means we can still explain
     failing eval cases after a restart.

  Your points
  - Hook results. Allow, Block(reason) and Pause(reason, payload) are three
    separate types. The loop handles Block and Pause through shared code, but
    only Pause ends the turn as paused.
  - Policy out of agentcore. The runtime keeps only mechanisms: hooks, atomic,
    idempotent, retry, verify, and opaque tags and payload. One write per turn
    is a before_tool hook in agent_service that counts the write tag. The
    pending action is an opaque JSON payload the runtime stores in
    session.state["pending"] and never reads. The boundary test (commit 1)
    checks that agentcore imports no agent_service or mock_hospital and uses no
    hospital words.
  - Order for book (1.6/1.7 conflict). The registry executor owns the order. The
    tool supplies run (one attempt), an optional verify, and a retry policy.
    The sequence is:
    a. Attempt run.
    b. On a definite ToolFailed, stop, with no verify because nothing changed.
    c. On Retryable or Unknown, retry the same input object, which holds the
       stored key, if the tool is idempotent and allows it.
    d. Otherwise call verify.
    e. End with one of Done, Failed or Unknown.

    Unknown appears only if verify itself fails, or a tool with no verify (such
    as payment_link) times out. It becomes a handoff.
  - Failure after a write. State and history are saved separately, and a failed
    turn rolls back history only. Around each atomic call the runtime saves
    inflight before and the outcome after, each with a state_saved trace event.
    LoopResult.outcomes lets the service say honestly that the booking went
    through. The next turn tells the model any outcome it hasn't been told. If
    inflight is still set at the start of a turn, the runtime calls that tool's
    verify before the model runs.
  - Phase 3 note. The model's read-back may differ from the stored payload. I
    logged the two options: code renders canonical facts and an after_model hook
    checks the reply contains them, or code sends the read-back itself.
  - Status block. I removed the stale open items. The remaining open ones are
    the measured timeouts, the history-trimming check (both in commit 8), and
    the Phase 3 items.
  - docs/flow.md. It has mermaid diagrams for the /chat turn, the agent loop and
    the tool executor, plus tables of what is stored where and who owns what.
    It is marked as design only until code exists.
